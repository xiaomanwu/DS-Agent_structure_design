# 指标定义与指标字典知识库

> 本文档是 Agent 的指标定义知识来源（RAG 可检索），也是指标字典治理流程的规范说明。
> Agent 在「指标注册 / 指标口径 / 指标管理」类问题上会引用这里的准则。

## 1. 指标分层

| 层级 | 定义 | 示例 | 在语义层中的形态 |
| --- | --- | --- | --- |
| 原子指标 | 最细粒度的可加事实，不再拆分 | `orders`（订单数）、`gmv`（成交额）、`sessions`（会话数） | additive：`SUM(column)` |
| 派生指标 | 原子指标 + 修饰词（时间/渠道/人群） | 「近7天新客 GMV」 | 原子指标 + WHERE 过滤 |
| 比率指标 | 分子分母都先聚合、再相除 | `conversion_rate = orders/sessions`、`aov = gmv/orders` | ratio：`SUM(a)/NULLIF(SUM(b),0)` |
| 复合指标 | 引用其他指标再运算 | `gmv_per_buyer = gmv/buyers`、`利润率 = (gmv-成本)/gmv` | 分解为已有指标的 SQL 表达式 |

**铁律：比率指标必须先聚合分子分母、再相除，绝不能对行级比率求平均。**
平均「每天的转化率」和「总转化率」是两个数；字典里必须写清用哪个。

## 2. 一个合格指标定义的要素

注册指标时必须能回答以下六问，缺一不可：

1. **分子/分母**：SQL 片段或底层列名；分母为 0 时如何处理（NULLIF 置 NULL，而不是报错或填 0）。
2. **去重口径**：用户数是 `COUNT(DISTINCT user_id)` 还是行数？同一用户一天多单算几次？
3. **时间窗与时区**：自然日按哪个时区切（UTC+8 vs UTC）；「昨日」的边界时刻。
4. **过滤条件**：是否剔除退款单、测试订单、内部流量；是否只算已支付状态。
5. **单位与方向**：单位（CNY/%/单）；方向（越高越好 / 越低越好，如退款率）。
6. **适用表**：定义绑定在哪个物理表上，换表即换定义，必须重新注册。

## 3. 常见口径坑（注册前自查）

- **UV/PV 混淆**：会话数（sessions）≠ 访客数（users）；转化率分母用错会系统性偏差。
- **比率再聚合**：渠道日报的转化率不能由各日转化率平均得到，必须分子分母相加后重算。
- **GMV vs 营收**：GMV 通常是下单口径（含未支付/含退款），营收是确认口径；两者差在「支付成功率 × 退款率」。Agent 的知识库中 GMV=SUM(gmv)，revenue 是它的别名——若业务上两者不同，必须拆成两个指标，不能共用别名。
- **退款率分子分母同源**：退款率 = 退款单/订单，两者必须是同一时间窗、同一过滤条件下的量。
- **时区漂移**：同一份日志按 UTC 与 UTC+8 切日，日环比可能差出 2-3 个百分点；跨区团队务必在字典里写明时区。
- **新客定义漂移**：新客 = 首次成交？首次访问？首日注册？实验与新客分析混用口径会得到相反结论。

## 4. 命名规范

- 小写下划线：`gmv_per_session`，禁止中文/空格/连字符直接做指标名。
- 比率类以 `_rate` 结尾，人均类以 `_per_` 连接，留存类以 `_retention` 结尾。
- 别名（aliases）用于自然语言识别：中文常用叫法 + 英文缩写都应登记（如 cvr、客单价）。
- 同名指标跨表不同定义时，加表前缀或在描述中显式声明差异。

## 5. 治理流程（注册 → 生效 → 下线）

1. **注册**：提供名称、分子/分母、别名、单位、方向、描述、绑定表；Agent 自动校验列是否存在。
2. **生效**：校验通过后指标进入语义层，自然语言查询/诊断/归因立即可用，全链路同口径。
3. **评审**：字典记录创建时间与负责人；口径变更应「新增 v2 + 弃用 v1」，不要原地改定义。
4. **下线**：`status=deprecated` 而非物理删除，保留可追溯性；历史报表引用不断链。

## 6. 与 Agent 的结合

- 语义层（`ds_agent/semantic.py`）保存**预置指标**，是所有下游工具（SQL、异常检测、归因、报告）的唯一口径来源。
- 指标字典（`ds_agent/metric_dict.py`）保存**用户注册的自定义指标**，注册即生效进语义层，并持久化到 JSON，重启不丢。
- 「这个指标怎么算 / 口径是什么」类问题走知识库 RAG（含本文档）；「注册 / 列出 / 下线指标」走指标字典管理。
