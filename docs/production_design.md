# 生产环境设计差异 / Production design differences

> 本文回答一个问题：**如果把 DS-Agent 推进生产环境，设计模式要改什么，什么不需要改。**
> 当前项目形态是"单机分析工作台"（单进程、单文件数仓、内存会话），生产形态则是一套
> 面向多用户、可审计、可运维的服务体系。

## 一、总体对比

| 维度 | 当前形态（工作台） | 生产形态（服务化） |
| --- | --- | --- |
| 进程模型 | 单进程 FastAPI + 全局单例 Agent | 多副本无状态 API + 独立 worker 池 + 任务队列 |
| 数据层 | 本地 DuckDB 单文件 | 企业数仓（只读副本）+ 连接器 + 查询下推与资源队列 |
| 会话状态 | 进程内存 dict | Redis / 数据库，按 user_id 隔离，可过期 |
| 鉴权 | 无（本机工具） | SSO/OIDC + RBAC + 行级权限（RLS）+ 全链路审计 |
| LLM 调用 | 同步直调，失败回退规则 | 超时/重试/熔断、多模型路由、成本预算与限流 |
| 长任务 | 同步阻塞（因果森林/合成控制秒级） | 入队异步执行，SSE/Webhook 推进度 |
| 模型资产 | 临时训练、无版本 | 模型注册表：版本、指标、审批、影子部署、回滚 |
| 监控 | 用户主动问"漂移了吗" | 周期调度跑 `monitor_report`，告警推 IM/电话 |
| 语义层 | `semantic.py` + 指标字典（内存） | 版本化建模文件（Git 管理）+ 变更评审 + 灰度发布 |
| 配置 | `.env` + 网页面板 | 配置中心 + 密钥管理（KMS/Vault），密钥不落盘 |
| 可观测性 | `tool_calls` 记录在回复里 | 结构化日志 + OpenTelemetry 追踪 + golden-QA 回归 |

## 二、必须改变的设计模式

### 1. 从"单例 Agent"到"无状态服务 + 会话外置"
`web.py::AgentHolder` 每进程一个 Agent、`session` 存内存——多副本下会话分裂，
重启即失忆。生产做法：Agent 变成**无状态计算单元**，`session / findings / 指标字典`
外置到 Redis（TTL 管理），请求携带 `user_id`，任何副本可服务任何请求。

### 2. DuckDB 单文件 → 数仓连接器 + 只读下推
DuckDB 适合单机分析；生产数据在数仓里。改造点：
- `tools/sql` 增加 Trino/BigQuery/ClickHouse 等适配器，DuckDB 保留为本地缓存层；
- 只读护栏（白名单、行数上限、语法校验）下沉到**连接器层**，所有入口共用；
- 大查询走资源队列（并发上限、超时、成本上限），防止一个因果森林拖垮数仓。

### 3. 长任务异步化
`monitor_report`、`train_model`、合成控制在生产数据量下是分钟级任务。引入任务队列
（Celery/Arq/Temporal）：`POST /api/chat` 秒回 `task_id`，SSE 推送阶段进度
（①预处理→②特征工程→③建模→④SHAP），失败时**重规划逻辑在 worker 内重试**。

### 4. 权限与审计进到工具层
当前任何会话可查全库。生产必须：
- RBAC → 工具级授权（没有实验权限就路由不到 `experiment_*`）；
- RLS → 语义层自动注入 `WHERE region = :user_region`；
- 每次分析的**问题、SQL、数据快照指纹、结论**落审计表——这正是"结论必证"设计的延伸。

### 5. 模型注册与影子部署
`train_model` 的产物现在只在回复里。生产闭环：
训练 → 注册表（版本/AUC/Brier/训练数据指纹）→ **影子部署**（新旧模型并行打分，
`monitor_report` 对比漂移与衰减）→ 灰度切流 → 回滚按钮。监控模块的
`PSI/AUC 阈值` 就是切流与回滚的触发器。

### 6. 知识库的版本化与评审
"改 Markdown 即生效"在单机是真优势，在生产则要加**评审门**：SQL 知识库（指标口径）
变更走 PR 评审 + golden-QA 回归通过才合并——308→321+ 测试正是合并门禁。

## 三、不需要改变的设计（这是重点）

1. **确定性工具层**：统计引擎（stats/、tools/）在两种形态里完全一致——这是
   "LLM 可选"架构的红利：LLM 只做意图识别与分发，换环境不动引擎。
2. **失败重规划循环**：`ranked_intents` + 次优重试是纯进程内逻辑，worker 里照跑。
3. **MCP 接口**：生产化后 `ds-agent-mcp` 直接变成内部 Agent 平台的标准化入口。
4. **置信卡 / 检验面板 / 结论先行**：治理越严格，这些结构化证据越值钱。
5. **金标准评测集**：从"本地回归"升级为"发布门禁 + 线上抽样对账"。

## 四、迁移路径建议

分三步，每步独立可用：

1. **服务化**（约 1–2 周）：多 worker + Redis 会话 + 任务队列 + Docker Compose——
   解决并发与可靠性，数据层不动；
2. **接数仓**（约 2–4 周）：连接器抽象 + RLS + 审计表——解决"能给谁看什么数据"；
3. **平台化**（长期）：模型注册表、语义层 Git 化、线上监控调度、评测门禁——
   解决"几十个团队同时用而不失控"。

> 一句话：**换掉的是载体（进程、存储、权限、调度），不变的是内核（确定性统计引擎 +
> 证据化结论 + 知识库驱动的成长机制）。**
