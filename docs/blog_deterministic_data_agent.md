# 为什么 Data Agent 应该是确定性的
## ——一个 LLM-optional 数据分析智能体的方法论实践

> **写作说明**：本文由 AI 辅助撰写，人工审核进行中。文中所有技术论断均对应
> [DS-Agent](https://github.com/xiaomanwu/ds-agent) 仓库中可运行、被测试锁定的代码，
> 欢迎对照源码与测试验证。观点与方法思路是项目的主要贡献，细节实现欢迎指正。

**摘要**：市面上的 Data Agent 几乎都是"相关性机器"——它们能告诉你 GMV 跌了，却说不清跌的原因
可不可信；能生成漂亮的图表，却给不出一张随结论附带的检验表。本文以 DS-Agent 的实践为例，
论证数据Agent 的正确分层方式：**统计与因果是确定性代码，LLM 只是可选的编排层**，
并给出三条可复用的设计原则。

---

## 一、问题的起点：LLM 做数据分析错在哪

让 LLM 直接分析数据的失败模式是结构性的，不是提示词能修复的：

1. **不可复现**。同一个问题问两次，p 值可能不一样——因为模型每次"重新发明"了检验方法。
   科学结论的基本要求是"同样数据同样答案"，LLM 现场写分析代码恰恰做不到这一点。
2. **统计幻觉**。模型会自信地选错检验（配对数据用独立样本 t 检验）、忽略多重比较、
   在 SRM（样本比例失配）的实验上照常读数。错误不是随机的，而是系统性地偏向
   "看起来像分析"的输出。
3. **无口径治理**。"GMV 含不含退款？"——通用模型不知道你的公司口径，也不想知道。

注意：这些问题都不是"模型不够聪明"的问题，而是**架构把不确定性放错了位置**的问题。
统计推断本身应该是确定性的；不确定的只有"用户想问什么"。

## 二、DS-Agent 的分层答案：LLM 可选，确定性优先

DS-Agent 把系统切成六层，关键决策是**把 LLM 完全挤出数字的生成路径**：

```
用户问题
   ├─► ① 意图路由    规则打分为主；LLM planner 可选，失败即回退
   ├─► ② 能力处理器  20+ 个（诊断/实验/因果/建模/抽样/看板…）
   ├─► ③ 工具层      每个分析领域一个确定性模块
   ├─► ④ 统计原语    功效、检验、CUPED、BH、抽样——全层共用
   ├─► ⑤ 数据层      语义层（口径唯一来源）+ 数仓
   └─► ⑥ 横切设施    置信卡 · 图表 · 报告 · RAG 知识库 · 指标字典
```

- **不配 LLM，全部功能照常可用**。路由是打分规则，分析是测试过的代码，输出是模板化的
  结论先行叙述。LLM 只在三个位置做增强：复杂意图的编排、语义层之外的灵活 SQL
  （过只读护栏后执行）、以及把统计结果翻译成人话。
- **数字永远来自 ④**。z 值查表、Cochran 公式、TWFE 回归——这些是 `stats/` 层的
  纯函数，被单元测试锁死。LLM 拿到的是算好的数字，任务只是解释它。

## 三、三条可复用的设计原则

### 原则 1：结论必证（Evidence attached）

每类分析的输出自动附带检验依据：诊断结论跟着季节性基线的 p 值，因果效应跟着
95% CI 和安慰剂反驳检验，实验读数先过 SRM 门再谈指标。这不是"加个表格"的产品功能，
而是**把统计规范编码进输出契约**——用户想跳过证据都跳不过。

### 原则 2：口径唯一（One caliber）

所有工具引用同一个语义层；新指标注册时要过数仓校验，之后全链路生效。
问数、看板、报告、异动诊断看到的 GMV 永远是同一个 GMV。Data Agent 的信任
不来自模型，来自**口径的一致性**。

### 原则 3：能力随知识库成长（Knowledge-base-driven growth）

Agent 的语义识别与判断不靠微调，靠四类可迭代的知识库：
SQL 知识库（语义层+指标字典）、企业知识库（RAG 语料）、工具使用知识库（方法论文档+
registry）、优秀报告知识库（结论先行的模板）。改一个 Markdown 文件即生效；
同时 318 个测试锁定既有行为，**迭代不会回退**。模型权重不变，Agent 变聪明。

## 四、如何证明它是可信的：金标准评测集

开源数据 Agent 最大的信任赤字是"你怎么知道它算得对"。DS-Agent 的答案是把
答案冻结成评测集：`benchmarks/golden_qa.jsonl`，18 个跨能力用例（中英混合），
期望值来自种子化数仓的确定性输出——样本量 2,452、DID ATT 275,432.40、
分类 AUC 0.8023……一条命令复跑：

```bash
python scripts/run_benchmark.py   # 18/18 passed (100%)
```

期望值改动必须在同一个提交里写明方法论理由。这套机制把"可复现"从口号变成了
CI 可执行的约束。

## 五、它应该被怎么用：MCP / Skill 形态的能力层

DS-Agent 的定位不是"又一个 ChatBI"，而是**统计引擎能力层**：
`ds-agent-mcp` 以零依赖的 stdio MCP server 暴露 5 个工具（自然语言全流程、
比例/均值样本量、知识检索、指标列表），任何 MCP 客户端（Claude、千问 CLI、IDE）
都能挂载。分工很清晰：**宿主 LLM 负责对话与编排，这个引擎保证每个数字
可复现、可审计、有检验依据**。

## 六、诚实的边界

- 语义层是手写的，没有自动 schema 推断；SQL 护栏是正则 + 只读连接，不是完备解析器；
- 归因是贪婪式剥洋葱（非 Shapley 分解），每步报告解释比例；
- PSM 只平衡观测到的协变量，隐性选择偏差要靠 AIPW 与敏感性分析兜底；
- 企业级治理（行级权限、连接器矩阵、多人协作）不在当前范围内——这也是我们判断
  它更适合做开源能力层而非商业产品的直接原因。

## 结语

Data Agent 的竞争力排序应该是：**统计正确性 > 口径治理 > 交互体验**，
而当前市场把精力基本花在了第三项。把不确定性限制在"理解用户"这一层，
让"生成结论"回归确定性代码——这个思路不新，但在 LLM 浪潮里值得被重新大声说出来。
